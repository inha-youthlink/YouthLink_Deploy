# YouthLink k3s 배포 계획 (EC2 단일 노드)

실행 명령은 `README.md`를 따른다. 이 문서는 무엇을 어떤 순서로 하는지와 그렇게 정한 이유(9절)를 정리한다.

## 1. 목표 구성

```
인터넷 ─▶ EC2 :80 ─▶ Traefik(Ingress) ─┬─ /api/* ─▶ youthlink-rag   (Deployment, FastAPI)
                                       └─ /*     ─▶ youthlink-front (Deployment, nginx + React 빌드 결과)

youthlink-etl   CronJob  매일 04:00 KST       정책 적재 → 청크 생성 → 임베딩
ragas-eval      Job      필요할 때 수동 실행   RAG_BASE_URL=http://youthlink-rag:8000 (클러스터 내부 호출)
DB              클러스터 밖 RDS PostgreSQL(pgvector)
```

| 구성 요소 | 원본 저장소 | k8s 리소스 | ECR 저장소 | 외부 노출 |
| --- | --- | --- | --- | --- |
| RAG | `YouthLink_RAG` | Deployment + Service + ConfigMap | `youthlink/rag` | `/api`만 (`/internal`, `/health`는 내부 전용) |
| 프론트 | `YouthLink_Front` | Deployment + Service | `youthlink/front` | `/` |
| ETL | `youthlink-data-pipeline` | CronJob + ConfigMap | `youthlink/etl` | 없음 |
| 평가 | `rag_ragas_evaluation` | Job + ConfigMap | `youthlink/ragas-eval` | 없음 |

> 프론트와 RAG를 같은 주소(Ingress) 아래에 두어 프론트의 상대경로 `/api` 호출이 CORS 설정 없이 그대로 동작한다. ETL은 매일 정해진 시간에, 평가는 실행할 때마다 LLM 비용이 들어 필요할 때만 한 번씩 띄운다.

## 2. 저장소 역할 (CI/CD는 이 저장소에서만)

| 저장소 | 맡는 일 | 배포 관련 파일 |
| --- | --- | --- |
| 앱 저장소 4개 | 소스코드 관리만 | 없음 |
| `YouthLink_Deploy` (이 저장소) | 이미지 빌드·push, 매니페스트, 일반 설정, 배포, 평가 실행 | Dockerfile, k8s yaml, workflow, 문서 |

```
deploy workflow (수동 실행: 앱, 앱 저장소 ref, 빌드 여부)
  ① 앱 저장소를 그 ref로 checkout (읽기 전용 토큰)
  ② apps/<앱>/Dockerfile로 이미지 빌드 → ECR에 커밋 SHA 태그로 push
  ③ k8s/<앱>/overlays/prod/kustomization.yaml의 이미지 태그를 그 SHA로 바꿔 커밋 (배포 이력)
  ④ EC2의 self-hosted 러너에서 kubectl apply -k k8s/<앱>/overlays/prod → 그 앱만 새 이미지로 교체
```

| 입력 | 값 | 설명 |
| --- | --- | --- |
| `app` | `rag`, `front`, `etl`, `ragas-eval`, `common` | `common`은 namespace·ingress 적용만 (빌드 없음) |
| `ref` | 기본 `main` | 빌드할 앱 저장소의 브랜치·태그·커밋 |
| `build` | 기본 `true` | `false`면 빌드 없이 현재 매니페스트만 적용 (설정 변경, 되돌리기) |

`ragas-eval`은 이미지 빌드와 태그 커밋까지만 하고 적용하지 않는다. 평가 실행은 `evaluate` workflow로 한다.

### 폴더 구조 (kustomize base/overlays)

```
YouthLink_Deploy/
├─ README.md                         실행 명령
├─ docs/배포계획.md                  이 문서
├─ apps/                             이미지 빌드용 Dockerfile (앱 저장소는 건드리지 않음)
│  ├─ rag/        Dockerfile, Dockerfile.dockerignore
│  ├─ front/      Dockerfile, Dockerfile.dockerignore, nginx.conf
│  ├─ etl/        Dockerfile, Dockerfile.dockerignore
│  └─ ragas-eval/ Dockerfile, Dockerfile.dockerignore
├─ k8s/
│  ├─ common/                        모든 앱이 공유하는 리소스
│  │  ├─ base/      kustomization.yaml, namespace.yaml, ingress.yaml
│  │  └─ overlays/prod/ kustomization.yaml
│  ├─ rag/
│  │  ├─ base/      kustomization.yaml, deployment.yaml, service.yaml
│  │  └─ overlays/prod/ kustomization.yaml (이미지 태그), config.env (일반 설정)
│  ├─ front/
│  │  ├─ base/      kustomization.yaml, deployment.yaml, service.yaml
│  │  └─ overlays/prod/ kustomization.yaml
│  ├─ etl/
│  │  ├─ base/      kustomization.yaml, cronjob.yaml
│  │  └─ overlays/prod/ kustomization.yaml, config.env
│  ├─ load-regions/                  지역 마스터 최초 1회 적재 (ETL 이미지, etl-secrets 사용)
│  │  ├─ base/      kustomization.yaml, job.yaml
│  │  └─ overlays/prod/ kustomization.yaml
│  └─ ragas-eval/
│     ├─ base/      kustomization.yaml, job.yaml
│     └─ overlays/prod/ kustomization.yaml, config.env
├─ scripts/ecr-refresh.sh            ECR pull 토큰 갱신 (EC2 cron)
└─ .github/workflows/
   ├─ deploy.yml                     빌드·push → 태그 커밋 → apply -k k8s/<앱>/overlays/prod
   └─ evaluate.yml                   입력: run/route/baseline → 이전 Job 삭제 → 평가 Job 적용
```

| 위치 | 담는 것 | 바꾸는 때 |
| --- | --- | --- |
| `<앱>/base/` | 환경과 무관한 기본 yaml. 리소스 종류마다 파일 하나 (deployment, service, cronjob, job) | 포트, 프로브, 리소스 한도처럼 구조가 바뀔 때 |
| `<앱>/overlays/prod/kustomization.yaml` | base를 가져와 운영 값만 덮어씀. 이미지 태그(`images`), ConfigMap 생성(`configMapGenerator`) | 배포할 때마다 (태그, workflow가 수정), 설정 바꿀 때 |
| `<앱>/overlays/prod/config.env` | 앱 일반 설정 `KEY=VALUE` (비밀값 없음) | 설정 바꿀 때 |
| `common/` | namespace, ingress | 경로 규칙이 바뀔 때 |

> 앱 저장소는 코드만 관리하고, "무엇을 언제 어떤 설정으로 띄울지"는 전부 이 저장소가 정한다. 이 저장소의 커밋 기록이 곧 배포 기록이다.

## 3. 환경변수 관리

| 종류 | 예 | 보관 위치 | 클러스터 반영 | 바꾸는 방법 |
| --- | --- | --- | --- | --- |
| 일반 설정 | 모델명, `RAG_BASE_URL`, `LLM_MAX_CONCURRENCY` | `k8s/<앱>/overlays/prod/config.env` (`configMapGenerator`가 읽음) | `apply -k` 시 ConfigMap 생성 | 값 수정·커밋 후 deploy workflow (`build: false`) |
| 비밀값 | `OPENAI_API_KEY`, `DATABASE_URL`, `YOUTH_API_KEY` | 클러스터 Secret에만 (git·GitHub에 두지 않음) | EC2에서 `kubectl create secret`으로 직접 생성 | Secret을 다시 만든 뒤 `kubectl rollout restart` |
| 프론트 빌드 변수 | `VITE_API_BASE`, `VITE_MOCK_FEATURES` | 이 저장소 GitHub Variables | 이미지 빌드 시 `--build-arg`로 넣어 JS 파일에 고정 | 값 수정 후 프론트 이미지를 다시 빌드 |

| 동작 | 이유 |
| --- | --- |
| ConfigMap 값만 바꿔도 Pod가 다시 뜸 | `configMapGenerator`는 내용이 바뀌면 이름 끝 해시가 바뀌고, 그 이름을 참조하는 Deployment도 바뀐 것으로 보고 재시작한다 |
| 비밀값은 workflow가 건드리지 않음 | 거의 바뀌지 않는 값이라 클러스터 한 곳에만 둔다. 이 저장소에 쓰기 권한이 있어도 비밀값을 볼 수 없다 |
| 비밀값을 바꾸면 재시작이 필요 | Secret을 환경변수로 받으므로 실행 중인 Pod에는 반영되지 않는다 |
| 프론트 변수는 재빌드가 필요 | Vite는 `VITE_*` 값을 빌드할 때 JS에 써 넣어서, 실행 중에 환경변수로 바꿀 수 없다. 기본 API 경로가 상대경로 `/api`라 비워 둬도 된다 |

| Secret | 사용 | 키 | `DATABASE_URL` 형식 |
| --- | --- | --- | --- |
| `rag-secrets` | RAG | `OPENAI_API_KEY`, `OPENAI_BASE_URL`, `DATABASE_URL` | `postgresql+asyncpg://` |
| `etl-secrets` | ETL, 지역 적재 | `YOUTH_API_URL`, `YOUTH_API_KEY`, `OPENAI_API_KEY`, `OPENAI_BASE_URL`, `DATABASE_URL`, `VWORLD_API_KEY`, `VWORLD_API_DOMAIN` | `postgresql://` |
| `ragas-eval-secrets` | 평가 | `OPENAI_API_KEY`, `OPENAI_BASE_URL`, `DATABASE_URL` | `postgresql://` |

> `OPENAI_BASE_URL`은 `bedrock-*` 모델을 부르는 프록시 주소다. 이 저장소가 공개라 `config.env`가 아니라 Secret에 넣는다.

## 4. 배포 전에 맞출 것

| # | 항목 | 현재 | 바꿀 것 | 담당 |
| --- | --- | --- | --- | --- |
| 1 | 임베딩 모델 | RAG·ETL 코드 모두 `text-embedding-3-small`(1536) | Titan(1024)으로 통일 후 `policy_chunk` 재임베딩. ETL `config.env`의 `OPENAI_EMBEDDING_MODEL`도 함께 변경 | RAG·ETL |
| 2 | Bedrock 프록시 주소 | 아직 지정하지 않음 | 세 Secret에 같은 `OPENAI_BASE_URL` 추가 | 배포 |

> 1번은 검색 결과가 틀어지는 문제라 평가 전에 끝내야 한다. 프론트 ↔ RAG API 경로 맞추기는 배포 성공 뒤로 미룬다 (8절).

## 5. 단계별 진행

| 단계 | 할 일 | 확인 방법 | 비고 |
| --- | --- | --- | --- |
| ① AWS 준비 | EC2(t3.small + swap 4GB) 생성, 탄력적 IP 연결 | SSH 접속 | EKS는 사용 불가 자원이라 k3s 사용 |
| | 보안 그룹: 22·6443은 내 IP, 80은 전체. RDS 보안 그룹에 EC2의 5432 허용 | EC2에서 `psql`로 RDS 접속 | |
| | EC2 IAM Role에 ECR 읽기 권한(`youthlink-ec2-role`) | `aws ecr describe-repositories` | Bedrock 호출 권한도 같은 Role |
| | ECR 저장소 4개(`youthlink/rag`, `front`, `etl`, `ragas-eval`) 생성 | 콘솔에 4개 보임 | |
| ② GitHub 설정 | 앱 저장소 4개 읽기 전용 fine-grained 토큰 발급 → Secret `APP_REPOS_TOKEN` | deploy workflow의 checkout 성공 | 기본 `GITHUB_TOKEN`은 다른 비공개 저장소를 못 읽음 |
| | Secrets `AWS_ROLE_ARN`, `AWS_REGION` 등록 | deploy workflow의 AWS 로그인 성공 | push Role은 `youthlink-github-deploy`, OIDC 조건 `repo:inha-youthlink/*`에 포함. 앱 비밀값은 GitHub에 넣지 않음 |
| | Settings → Actions → General: "Require approval for all outside collaborators", Workflow permissions "Read and write" | | 태그 커밋에 쓰기 권한 필요 |
| ③ k3s 설치 | k3s 설치 (metrics-server 끔), Docker 비활성화 | `kubectl get nodes`가 Ready | EC2에서 이미지를 빌드하지 않음 |
| | self-hosted 러너 설치 (이 저장소 Settings → Actions → Runners → New self-hosted runner, Linux x64, 라벨 `k3s`, `svc.sh`로 서비스 등록) | Actions 화면에 러너 Idle | 일반 사용자(`ec2-user`)로 설치. 빌드는 GitHub 러너, apply만 이 러너 |
| ④ 클러스터 기본 | deploy workflow (`app: common`) | `kubectl get ns youthlink` | namespace, ingress |
| | `ecr-refresh.sh` 설치 + root cron 6시간 주기 | `kubectl -n youthlink get secret ecr-pull` | ECR 토큰은 12시간이면 만료 |
| | Secret 3개 직접 생성 (3절 표) | `kubectl -n youthlink get secret` | 값은 명령에 직접 입력. 파일·저장소에 남기지 않음 |
| ⑤ 데이터 | deploy workflow (`app: etl`) | CronJob 생성 | |
| | `kubectl apply -k k8s/load-regions/overlays/prod`로 지역 마스터 1회 적재 | `policy_region` 행 수 | 최초 1회만 |
| | ETL CronJob 수동 1회 실행 | Job 성공, `policy_chunk.embedding` 채워짐 | RAG보다 먼저. 검색할 데이터가 있어야 함 |
| ⑥ 서비스 | deploy workflow (`app: rag`, `app: front`) | `http://<EIP>/`에 화면이 뜨고, `http://<EIP>/api/rooms`가 FastAPI 응답(JSON)을 주면 성공 | 채팅 동작은 확인 대상 아님 (API 경로 미정) |
| ⑦ 평가 | deploy workflow (`app: ragas-eval`)로 이미지 준비 후 evaluate workflow (`run`) | run `SUCCEEDED`, 로그의 `채점 실패` 건수 | LLM 비용 발생. ETL 실행 시간(04:00~06:00)은 피함 |
| | evaluate workflow (`route`) | 라우팅 정확도 집계 | |

> 데이터(⑤) → RAG(⑥) → 평가(⑦) 순서로 올린다. 앞 단계가 없으면 뒤 단계가 빈 결과를 내거나 실패한다.

### 배포가 EC2에 닿는 흐름

| 순서 | 어디서 | 일어나는 일 |
| --- | --- | --- |
| 1 | GitHub 웹 | deploy workflow 수동 실행 |
| 2 | GitHub 클라우드 러너 | 이미지 빌드 → ECR push → 이미지 태그 커밋 (빌드는 무거워서 EC2에서 하지 않음) |
| 3 | EC2 self-hosted 러너 | GitHub에 할 일을 묻고 있다가 apply 작업을 가져옴 (EC2 → GitHub 방향 연결) |
| 4 | EC2 self-hosted 러너 | EC2 안에서 `kubectl apply -k k8s/<앱>/overlays/prod` 실행 (localhost:6443) |
| 5 | k3s | 바뀐 이미지 태그를 보고 ECR에서 새 이미지를 받아 Pod 교체 |

> 러너를 EC2에 두는 이유는 보안이다. GitHub 클라우드에서 바로 `kubectl`을 쓰려면 6443을 인터넷에 열고 관리자 인증서(kubeconfig)를 GitHub에 맡겨야 한다. 러너는 EC2에서 GitHub으로 나가는 연결만 쓰므로 들어오는 포트를 열지 않고, 인증서도 EC2 밖으로 나가지 않는다.

| 러너 보안 설정 | 내용 |
| --- | --- |
| 저장소 전용 등록 | 조직이 아니라 이 저장소 Settings → Actions → Runners에서 등록. 다른 저장소의 workflow가 이 러너를 쓰지 못함 |
| 외부인 workflow 승인 필수 | Settings → Actions → General → "Require approval for all outside collaborators". 외부인 PR의 workflow는 승인 전까지 실행되지 않음 (Public 저장소일 때 필수) |
| 외부인 PR 승인 금지 | workflow 파일을 확인하기 전에는 승인하지 않음. 승인하면 그 코드가 EC2에서 실행됨 |

## 6. 배치 일정 (t3.small 메모리 기준)

| 작업 | 일정 | 메모리 limit | 겹치면 안 되는 작업 |
| --- | --- | --- | --- |
| ETL | 매일 04:00 KST (최대 2시간) | 512Mi | 평가 |
| 평가 | 필요할 때 수동 실행 (최대 2시간) | 1Gi | ETL |
| RAG | 상시 | 512Mi | |
| 프론트 | 상시 | 64Mi | |
| self-hosted 러너 | 상시 (대기 중) | 약 100~200MB | |
| k3s 시스템 | 상시 | 약 0.7~1GB | |

> 평가는 RAG·프롬프트·데이터를 바꾼 뒤처럼 결과를 보고 싶을 때만 Job으로 한 번 돌린다. ETL과 동시에 뜨면 메모리가 모자라므로 04:00~06:00은 피한다.

## 7. 운영

| 상황 | 방법 |
| --- | --- |
| 코드 수정 반영 | 앱 저장소에 push → deploy workflow (`app`, `ref` 선택) |
| 일반 설정 변경 | `config.env` 수정·커밋 → deploy workflow (`build: false`) |
| 비밀값 변경 | EC2에서 Secret 다시 생성 (`kubectl create secret ... --dry-run=client -o yaml \| kubectl apply -f -`) → `kubectl -n youthlink rollout restart deploy/<앱>` (CronJob·Job은 다음 실행부터 반영) |
| 되돌리기 | 태그를 바꾼 커밋을 revert → deploy workflow (`build: false`) |
| 평가 실행 | evaluate workflow (`run` / `route` / `baseline`) |
| ETL 즉시 실행 | `kubectl -n youthlink create job etl-manual-$(date +%s) --from=cronjob/youthlink-etl` |
| 로그 | `kubectl -n youthlink logs -f deploy/youthlink-rag`, 배치는 `logs -f job/<이름>` |

## 8. 이후 과제

| 과제 | 내용 |
| --- | --- |
| 프론트 ↔ RAG API 경로 | 프론트는 `/api/sessions`·`/api/policies`, RAG는 `/api/rooms` |
| HTTPS | 도메인 없이 CloudFront 앞단(`*.cloudfront.net`), 또는 도메인 구매 후 cert-manager + Let's Encrypt |
| 앱 저장소 테스트 | 배포 전에 각 저장소 테스트를 돌릴지 결정 (ETL 저장소에는 `tests.yml`이 있음) |
| ETL 실패 로그 보존 | `etl/logs/failed_policies.jsonl`이 컨테이너 안에 쓰여 Job이 끝나면 사라짐. 필요하면 PVC 또는 stdout 출력 |

## 9. 결정 기록

| 결정 | 이유 |
| --- | --- |
| 프론트를 k3s에 함께 올림 | 프론트 CSP가 `connect-src 'self'`이고 API 기본 경로가 상대경로 `/api`라, 같은 출처로 묶어야 CORS·CSP 수정 없이 동작한다. nginx 메모리는 약 10MB. `vercel.json`의 보안 헤더는 `apps/front/nginx.conf`로 옮겼다 |
| Ingress는 `/api`만 RAG로 | `/internal/pipeline`(평가 전용)과 `/health`는 외부에 노출하지 않는다. 평가는 클러스터 내부 Service 주소로 호출한다 |
| 이미지 빌드는 GitHub 러너, 레지스트리는 ECR | t3.small에서 빌드하면 메모리와 CPU 크레딧을 크게 쓴다. EC2의 Docker는 꺼서 메모리를 아낀다 |
| CI/CD를 이 저장소 하나로 | 앱 저장소를 수정하지 않고, 배포 시점·설정·이력을 한 곳에서 관리한다. 앱 저장소마다 클러스터 접근 권한을 둘 필요가 없다 |
| kustomize (base/overlays, `prod` 하나) | 이미지 태그를 overlay 한 줄로 바꾸고, `configMapGenerator`로 설정 변경 시 Pod가 자동 재시작된다. 환경이 하나라 overlay도 `prod`만 둔다 |
| 비밀값은 클러스터에 수동 생성 | 거의 바뀌지 않는 값이라 GitHub과 클러스터 두 곳에 두지 않는다. workflow는 Secret을 읽거나 쓰지 않는다 |
| 클러스터 접근은 self-hosted 러너 | 6443·22를 열지 않고 권한 요청도 필요 없다. 이 저장소 전용으로 등록하고 외부인 workflow는 승인 필수로 둔다 |
| ECR 인증은 호스트 cron 스크립트 | ECR 토큰은 12시간이면 만료된다. kubelet credential provider는 설치가 번거롭고 Pod에서 IMDS를 쓰려면 hop limit 설정이 필요해, EC2 IAM Role을 쓰는 호스트 cron이 6시간마다 `ecr-pull` Secret을 갱신한다 |
| `DATABASE_URL` Secret을 앱별로 분리 | RAG는 `postgresql+asyncpg://`(SQLAlchemy async), ETL·평가는 `postgresql://`(psycopg)를 쓴다 |
| 평가·지역 적재는 Job, 별도 폴더 | Job은 적용하는 순간 실행된다. 평가는 실행마다 LLM 비용이 들어 evaluate workflow로만, 지역 적재는 최초 1회만 적용한다 |
| ETL CronJob 설정 | 매일 04:00 KST(`timeZone: Asia/Seoul`). 전날 실행이 안 끝났으면 건너뛰도록 `concurrencyPolicy: Forbid`. 세 단계를 `&&`로 이어 앞 단계가 실패하면 뒤 단계를 건너뛴다 |
| 평가 동시 요청 4 | 평가와 RAG가 같은 LLM API 키(키당 동시 8)를 나눠 쓴다 |
